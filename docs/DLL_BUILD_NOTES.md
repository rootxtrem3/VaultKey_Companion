# Windows DLL prototype: build notes, failures, and reproduction

Status: **prototype only**. The DLL is not part of the `0.2.0` release, is not
wired into `scripts/build-release.sh`, and has not been loaded on Windows or
tested against a rev-D board.

This note records what broke while producing the prototype, what fixed it, and
how to reproduce each failure without touching a real device.

### Exact build command

Run from the repository root in this checkout:

```sh
GOOS=windows GOARCH=amd64 CGO_ENABLED=1 CC=x86_64-w64-mingw32-gcc \
go build -buildmode=c-shared -trimpath \
  -ldflags '-s -w -X main.version=0.1.0 -X main.commit=prototype -X main.buildDate=2026-11-17T00:00:00Z' \
  -o dist/vaultkey_windows_amd64.dll ./cmd/vaultkey-dll
```

The output must keep the exact basename `vaultkey_windows_amd64.dll`. cgo
embeds the DLL name in the export directory, so building the same source to
`foo.dll` produces a different layout and hash.

The command above reproduced this hash in the dirty working tree used to write
this note, because Go embeds the Git metadata (`vcs.revision`, `vcs.modified`).
Once the tree is committed or otherwise changed, that metadata changes and so
does the hash. In a source archive without `.git`, add `-buildvcs=false`; the
result is deterministic but has a different hash. The reproduction script does
that so it works from a copied tree.

## 2. Detailed failures

### 2.1 The release pipeline is `CGO_ENABLED=0`

`scripts/build-release.sh` builds six console binaries with `CGO_ENABLED=0`.
That pipeline correctly produces no DLL. Attempting to add `-buildmode=c-shared`
to it fails during the link step:

```text
-buildmode=c-shared requires external (cgo) linking, but cgo is not enabled
```

Reproduce:

```sh
GOOS=windows GOARCH=amd64 CGO_ENABLED=0 \
go build -buildmode=c-shared -o /tmp/vaultkey-cgo0.dll ./cmd/vaultkey-dll
```

Fix: keep the DLL out of the cross-build/release path and use a separate
cgo-enabled command. `make build`, `make release`, and the six release binaries
remain pure Go.

### 2.2 A host C compiler cannot target Windows

`CC` unset (or `CC=gcc`) makes Go invoke the host GCC while
`GOOS=windows`. The host compiler has no Windows headers:

```text
# runtime/cgo
gcc_libinit_windows.c:10:10: fatal error: windows.h: No such file or directory
   10 | #include <windows.h>
      |          ^~~~~~~~~~~
compilation terminated.
```

Reproduce:

```sh
GOOS=windows GOARCH=amd64 CGO_ENABLED=1 CC=gcc \
go build -buildmode=c-shared -o /tmp/vaultkey-hostcc.dll ./cmd/vaultkey-dll
```

Fix:

```sh
CC=x86_64-w64-mingw32-gcc
```

On Windows, use an MSYS2 mingw-w64 shell or a Visual Studio developer prompt
with a compatible `CC`; do not assume the default compiler is correct.

### 2.3 The Windows-only file and the stub

`cmd/vaultkey-dll/main.go` is guarded by `//go:build windows && cgo`.
`cmd/vaultkey-dll/stub.go` is guarded by `//go:build !windows || !cgo` and
contains only `func main() {}`.

Without the stub, a normal native build fails before compiling anything:

```text
package github.com/rootxtrem3/VaultKey_Companion/cmd/vaultkey-dll:
build constraints exclude all Go files in .../cmd/vaultkey-dll
```

Reproduce by removing `stub.go` from a copy and running `go build
./cmd/vaultkey-dll` on Linux.

The stub is deliberate: it keeps `go build ./...`, `go test ./...`, and
`go vet ./...` green on hosts that do not have a Windows C toolchain. Do not
delete it to "fix" a local build; build with the Windows target instead.

### 2.4 `<stdlib.h>` is required for `C.free`

`VKFree` calls `C.free`. If the cgo preamble only imports `"C"` without
`#include <stdlib.h>`, cgo cannot resolve the symbol:

```text
cmd/vaultkey-dll/main.go:558:3: could not determine what C.free refers to
```

Reproduce by deleting the `#include <stdlib.h>` line from a copy of
`main.go` and rebuilding.

The real preamble is:

```go
/*
#include <stdlib.h>
*/
import "C"
```

Two related rules:

- Returned strings are allocated by cgo. The caller must release them with
  `VKFree`, not with a different CRT's `free()`. A Windows host linked against
  a different C runtime can corrupt the heap otherwise.
- `VKCall` never returns a pointer into Go memory. Every success and error path
  returns a fresh `C.CString`.

### 2.5 `c-shared` still needs `func main()`

Even though the library is not an executable, a Go `main` package built with
`-buildmode=c-shared` must declare `main`:

```text
runtime.main_main·f: function main is undeclared in the main package
```

The file ends with:

```go
func main() {}
```

Do not remove it when cleaning up the package.

### 2.6 Architecture and toolchain must match

Only the amd64 DLL was built. Passing `GOARCH=arm64` with an amd64 mingw
compiler makes the C compiler assemble arm64 runtime stubs as x86:

```text
# runtime/cgo
/tmp/cc...s: Assembler messages:
gcc_arm64.S:30: Error: no such instruction: `stp x29,x30,[sp,'
gcc_arm64.S:34: Error: operand type mismatch for `mov'
...
```

Reproduce:

```sh
GOOS=windows GOARCH=arm64 CGO_ENABLED=1 CC=x86_64-w64-mingw32-gcc \
go build -buildmode=c-shared -o /tmp/vaultkey-arm64.dll ./cmd/vaultkey-dll
```

Fix: install `aarch64-w64-mingw32-gcc` and set `CC` to it. That toolchain was
not available in this environment, so **no arm64 DLL exists**. Do not publish
an arm64 artifact until it is built and loaded on arm64 Windows.

The same rule applies to 386: use an i686 toolchain and a matching `GOARCH`.

### 2.7 The Linux `.so` fallback silently builds only the stub

The prototype was originally checked with a Linux `.so` and Python `ctypes`
because a PE DLL cannot be loaded on Linux. That worked for the old test
artifact, but it does **not** work from the current source:

```sh
GOOS=linux GOARCH=amd64 CGO_ENABLED=1 \
go build -buildmode=c-shared -o /tmp/libvaultkey.so ./cmd/vaultkey-dll
```

The build succeeds, but `main.go` is excluded (`windows && cgo`) and `stub.go`
is included (`!windows || !cgo`). The resulting library exports nothing:

```sh
nm -D /tmp/libvaultkey.so | grep ' T VKCall$'
# no output
```

A Python caller then fails with:

```text
AttributeError: /tmp/libvaultkey.so: undefined symbol: VKCall
```

To reproduce the ABI test, use a throwaway copy:

```sh
mkdir -p /tmp/vk-abi
cp -r cmd internal go.mod /tmp/vk-abi/
rm /tmp/vk-abi/cmd/vaultkey-dll/stub.go
sed -i 's|^//go:build windows && cgo$|//go:build cgo|' \
  /tmp/vk-abi/cmd/vaultkey-dll/main.go
cd /tmp/vk-abi
GOOS=linux GOARCH=amd64 CGO_ENABLED=1 \
  go build -buildmode=c-shared -trimpath -o /tmp/libvaultkey.so ./cmd/vaultkey-dll
nm -D /tmp/libvaultkey.so | grep ' T VKCall$'
```

The tag change is test-only. Do not commit it; the shipped Windows DLL must
keep `windows && cgo`.

### 2.8 `c-shared` does not emit an import library

`go build -buildmode=c-shared` writes the DLL and a generated header. It does
not write an MSVC `.lib` or a mingw `.a`:

```sh
ls dist/*.a dist/*.lib
# ls: cannot access 'dist/*.a': No such file or directory
```

GNU ld can link directly against the DLL; MSVC needs an import library. Two
workarounds:

1. Generate a `.def` and import library with mingw:

   ```def
   LIBRARY vaultkey_windows_amd64.dll
   EXPORTS
   VKCall
   VKFree
   VKVersion
   VKSessionProtocol
   ```

   ```sh
   x86_64-w64-mingw32-dlltool -d vaultkey.def \
     -l libvaultkey_windows_amd64.a
   x86_64-w64-mingw32-gcc host.o -L. -lvaultkey_windows_amd64 -o host.exe
   ```

2. Load the DLL at runtime with `LoadLibraryEx` and `GetProcAddress`. This
   avoids both the import library and link-time CRT coupling, and lets the host
   report a missing DLL cleanly.

MSVC users can run `dumpbin /exports` and `lib /def:vaultkey.def /machine:x64`.
The DLL is x64 only.

### 2.9 The generated header and its ownership

`-o dist/vaultkey_windows_amd64.dll` also writes
`dist/vaultkey_windows_amd64.h`. cgo regenerates and overwrites that header on
every build. Do not hand-edit it; put host-side declarations in a separate
wrapper header if needed.

The generated declarations are:

```c
extern char* VKCall(char* cRequest);
extern void VKFree(char* pointer);
extern char* VKVersion(void);
extern int VKSessionProtocol(void);
```

Notes:

- The header already wraps the declarations in `extern "C"` for C++.
- `VKCall` takes `char*`, not `const char*`. A C++ caller with a string literal
  must copy it into a mutable buffer or cast explicitly.
- Keep the DLL basename and header basename in sync. Changing `-o` changes the
  header name and the export directory.
- Treat `VKCall`/`VKFree`/`VKVersion`/`VKSessionProtocol` as the ABI. Do not
  expose Go types across the boundary.

### 2.10 `gofmt` drift

`gofmt -l cmd/vaultkey-dll/*.go` reported `main.go` because one struct literal
had inconsistent field alignment. Fixed. The reproduction script checks this
so the DLL package stays formatted.

### 2.11 Mutating errors lost the `ambiguous` flag

This was a safety bug, not a compiler error.

`internal/vaultkey` wraps a lost mutating response in `*AmbiguousError`, whose
`Unwrap` returns the cause (often `context.DeadlineExceeded` or a write error).
The DLL's `classify` originally checked `context.DeadlineExceeded` first:

```go
case errors.Is(err, context.DeadlineExceeded):
    // classified as timeout
case errors.As(err, &ambiguous):
    // never reached for a wrapped timeout
```

The exit code was still `7`, but the response lost `"ambiguous": true` and the
"verify before retrying" hint. A UI could interpret that as a safe retry and
duplicate an add/update/delete.

Fix: check `*AmbiguousError` before its wrapped cause, matching
`internal/cli/app.fail`. The order is now:

```go
case errors.Is(err, context.Canceled):
case errors.As(err, &ambiguous):
case errors.Is(err, context.DeadlineExceeded):
```

The pure mapping now lives in `internal/dllapi/classify.go`, without a cgo or
Windows build tag; `cmd/vaultkey-dll/main.go` aliases its `Info`, `Usage`,
`Connection`, and `Classify` names. `internal/dllapi/classify_test.go` covers
both an ambiguous timeout and an ambiguous write error on Linux. The loaded-DLL
path still needs a host-side test: force a mutating timeout, then assert
`ok:false`, `"ambiguous":true`, and `"exit_code":7`.

### 2.12 Why the artifact hash changes

A rebuild can produce a different hash even when the Go source is identical.
The three observed causes are:

1. **Linker flags.** `-s -w` and the `-X main.version/commit/buildDate`
   values change the binary. The exact command above pins all of them.
2. **VCS metadata.** Go embeds `vcs.revision`, `vcs.time`, and
   `vcs.modified` when building inside a Git worktree. A copy without `.git`
   produces a different hash. Add `-buildvcs=false` for a source archive.
3. **Output basename.** cgo writes the DLL name into the PE export directory.
   Building the same code to `foo.dll` changes `.edata`, relocations, and the
   hash.

With the exact command and the same basename, two builds in this checkout
produced byte-identical files. The reproduction script builds in a copied tree
with `-buildvcs=false`, so it prints a different but deterministic hash.

## 3. Reproduce everything

```sh
./scripts/reproduce-dll-build.sh
```

Requirements:

```sh
# Debian/Ubuntu
sudo apt install golang mingw-w64 binutils-mingw-w64

# Arch
sudo pacman -S go mingw-w64-binutils mingw-w64-gcc
```

The script:

- copies `go.mod`, `internal/`, and `cmd/` into a temp directory;
- runs each expected failure and checks the exact error text;
- builds the supported Windows amd64 DLL;
- checks PE32+/x86-64, exports, KERNEL32 import, header generation, C and C++
  header compilation, and import-library linking;
- builds the Linux `.so` workaround and runs a `ctypes` ABI smoke test;
- runs `gofmt`, `go vet`, and `go test ./...` on the stub build;
- exits non-zero if any expected outcome changes.

Useful options:

```sh
./scripts/reproduce-dll-build.sh --keep     # keep the temp tree
./scripts/reproduce-dll-build.sh --no-abi   # skip the Linux .so test
```

The script never modifies the repository and does not need a device.

## 4. Validate without Windows

The Linux `.so` test proves:

- the C ABI exports the four expected symbols;
- `VKCall` accepts UTF-8 JSON and returns a NUL-terminated UTF-8 string;
- `VKFree` releases the returned string;
- `capabilities` reports `session_protocol: 1`;
- `status` without a device returns `not_open` / exit `3`;
- an unknown method returns `unknown_method` / exit `2`;
- malformed JSON returns `invalid_json` / exit `2`.

It does **not** prove:

- that Windows can load the PE DLL or resolve its UCRT imports;
- that the COM-port DCB, timeouts, DTR/RTS, and `ReadFile` behavior work;
- that the rev-D device authorizes CDC, keeps authorization while the handle
  is open, or revokes it on close/unplug;
- that the DLL survives unplug/replug, sleep/resume, or a busy port;
- that Defender/SmartScreen/code-signing policy allows the DLL.

Those require a Windows host and a rev-D board.

## 5. Known functional gaps in the prototype

These are not build failures, but they matter to a UI host.

- **No VID filtering on auto-detect.** `transport.Candidates()` enumerates
  `HARDWARE\DEVICEMAP\SERIALCOMM` and the DLL probes every port with `HELLO`.
  It does not walk USB registry entries for VID `303A`. Opening unrelated COM
  ports can toggle DTR and disturb other devices. Phase A in
  `docs/WINDOWS_AGENT_HANDOFF.md` adds the VID walk.
- **Lexicographic port order.** `COM10` sorts before `COM2`; natural sorting
  is not implemented.
- **Idle reads are not tolerated.** Windows `ReadFile` returns `(0, nil)` on a
  timeout. The `bufio.Reader` in `internal/vaultkey/client.go` turns 100 empty
  reads into `io.ErrNoProgress` (about 10 seconds at the configured 100 ms
  timeout). Short DLL calls are usually unaffected, but a long-lived session
  or `watch` can lose the reader while idle. Phase A adds an idle-resistant
  reader.
- **Discovery errors are classified as `internal`.** "No candidate ports",
  "no VaultKey answered", and "multiple VaultKey devices found" are plain
  `fmt.Errorf` values, so `classify` falls through to exit `1` instead of a
  connection error. Phase A should wrap them in typed errors.
- **`open` closes the current handle first.** If the new port fails, the old
  session is already gone. That is deliberate for Windows exclusivity, but the
  UI must re-authorize and re-open.
- **No automatic reconnect.** Unplug leaves a stale handle. The host must call
  `reconnect` or `open` again.
- **No `watch` or `doctor`.** The DLL is synchronous request/response only.
- **One call at a time.** A global mutex serializes `VKCall`; a slow request
  blocks every other request. There is no cancellation or progress callback.
- **No `pkg/session` yet.** The prototype wraps `internal/vaultkey`, not the
  planned public API. Rebuild it on `pkg/session` after Phase B.
- **No arm64 DLL.** Only amd64 was built.
- **No code signing.** Treat the DLL as unsigned prototype code; SmartScreen
  and Defender may block or quarantine it. Sign it before distribution.
- **UCRT/private API-set imports.** `file` reports Windows 10.00 and the import
  table includes `api-ms-win-crt-private-l1-1-0.dll`. Windows 10+ is the
  practical floor. Test on the oldest Windows version you intend to support.
- **No hardware validation.** No rev-D board was available.

## 6. Windows host checklist

When a Windows machine and a rev-D board are available:

1. Build with mingw-w64 or MSVC. Confirm the output is PE32+ x86-64 and
   `dumpbin /exports` lists all four symbols.
2. Load with `LoadLibraryEx` from an absolute path. Check `GetLastError` and
   confirm the UCRT dependencies resolve.
3. Call `VKVersion` and `VKSessionProtocol`; free the version string with
   `VKFree`.
4. Call `VKCall({"id":1,"method":"capabilities"})`; verify
   `session_protocol: 1` and the method list.
5. Call `open` with an explicit `COMx`; authorize CDC on the device first.
6. Call `status`, `time.get`, and `list`. Add one credential, list it, delete
   it, and verify the device UI reflects each change.
7. Close the handle and confirm the five-minute authorization is revoked.
8. Unplug while open, call `status`, and verify a clean connection error; then
   reconnect and re-authorize.
9. Force a mutating timeout (for example, unplug during
   `credentials.add`) and verify `"ambiguous": true` and `"exit_code": 7`.
10. Repeat from a C++ host and from the intended UI host. Do not call `VKCall`
    from `DllMain` or the loader lock.
11. Test on a clean Windows machine without the mingw toolchain installed.
12. Sign and timestamp the DLL before shipping it.
